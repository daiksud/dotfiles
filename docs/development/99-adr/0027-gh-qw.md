# ADR 0027: Replace gh-qwt with gh-qw

Adopt the `gh-qw` GitHub CLI extension in place of `gh-qwt` for repository
cloning and per-branch Git worktree management.

## Status

Accepted

## Context

[ADR 0008](./0008-gh-qwt.md) adopted `gh-qwt` (`daiksud/gh-qwt`) as the single
tool for cloning repositories and managing per-branch worktrees.
[ADR 0019](./0019-gh-qwt-ghq-layout.md) later followed its move to a
ghq-compatible layout, and [ADR 0023](./0023-pr-skills-gh-qwt-checkouts.md)
carved out an exception so the shared Pull Request skills could use a
`gh-qwt`-managed checkout without being rejected for carrying `qwt.managed`
metadata or moving the primary checkout off its pinned default branch.

`gh-qw` (`daiksud/gh-qw`) is the same author's from-scratch redesign that
covers the same two jobs — cloning/listing repositories under a
`<host>/<owner>/<repo>` identity, and creating per-branch linked worktrees —
but is not a drop-in replacement:

- It has **no `path` command**. `gh qwt path <spec>` printed a single
  resolved (or deterministic planned) absolute path; `gh-qw` only prints
  identities (`list`) or full paths for matching identities
  (`list --exact --full-path`), so a single lookup becomes two.
- It writes **no managed metadata**. `gh-qwt` recorded `qwt.managed`,
  `qwt.identity`, `qwt.defaultbranch`, and `qwt.worktreeroot` in
  repository-local Git config. `gh-qw` treats Git as the only source of
  truth and never touches Git config for its own bookkeeping.
- Its main worktree is **never pinned to a branch**. `gh-qwt` validated that
  its primary checkout stayed on `qwt.defaultbranch` before running any
  management command, which is exactly what ADR 0023 had to work around for
  the PR skills. `gh-qw`'s main worktree is an ordinary clone with no such
  constraint.
- It **owns its own root configuration**. `gh-qwt` shared ghq's `GHQ_ROOT` /
  `ghq.root` and depended on the real `ghq` binary for compatibility.
  `gh-qw` resolves `GHQW_ROOT` / `~/.config/ghqw/config.toml` independently,
  defaulting to `~/ghqw` for repositories and
  `~/.local/share/ghqw/worktrees` for linked worktrees, and reads `ghq.*` Git
  configuration only inside `gh qw migrate`, to locate legacy repositories.
- It performs its **own GitHub account selection** for `get` and
  `worktree add` (explicit token, cached choice, owner match, sole account,
  or interactive prompt), independent of and in addition to this
  repository's own `gh-account.zsh` identity switching.

Continuing to depend on `gh-qwt` means depending on a tool whose own author
has moved development to `gh-qw`; there is no reason to keep integrating
against the tool being replaced once its intended successor is available.

## Decision

Replace `gh-qwt` with `gh-qw` for interactive repository cloning and
per-branch worktree management, using `gh-qw`'s default configuration.

- Install `daiksud/gh-qw` in place of `daiksud/gh-qwt` in
  `scripts/100-gh-extensions.sh`. While changing this, also fix the
  installed-extension check: `gh extension list`'s first tab-separated
  column is the local command name (for example `gh qw`), not the
  `<owner>/<repo>` spec, so the previous `awk '{print $1}' | grep -qx
  "${extension}"` never matched anything and reinstalled on every run. The
  check now derives `gh <name>` from the extension spec and compares against
  that column.
- Remove `brew "ghq"` from `Brewfile`. `gh-qw` does not read or require the
  standalone `ghq` binary during normal operation.
- Keep `gh-qw`'s default roots (`~/ghqw`, `~/.local/share/ghqw/worktrees`).
  Do not add a `~/.config/ghqw/config.toml`; there is no reason to override
  either default for this repository's use.
- Replace the shared fzf selector `dotfiles/zsh/qwt-select.zsh`
  (`qwt-select-path`) with `dotfiles/zsh/repository-select.zsh`
  (`repository-select-path`). Because `gh-qw` has no `path` command,
  resolution is now a two-step lookup: list identities with
  `gh qw list --worktree`, then resolve the selected identity to an absolute
  path with `gh qw list --exact --full-path` for a bare
  `<host>/<owner>/<repo>` identity, or `gh qw list --worktree --exact
  --full-path` when the identity carries an `@<branch>` suffix. The
  `--worktree` flag must be omitted for a bare identity because
  `--worktree --exact` without a suffix matches a repository's main worktree
  **and every one of its linked worktrees**. `list` exits `0` with empty
  output on no match, so the selector now treats empty output, not a
  nonzero exit status, as "not found".
- Rename `go-to-qwt-repository.zsh` to `go-to-repository.zsh` and
  `edit-qwt-repository.zsh` to `edit-repository.zsh`, dropping the
  tool-specific name now that the selector is not `gh-qwt`-specific. The
  `ggr`/`egr` aliases and the `C-]` keybinding are unchanged.
- Simplify `pr-create`, `pr-fix`, and `pr-merge`: remove every
  `qwt.managed`/`qwt.defaultbranch` reference and `pr-create`'s "the gh-qwt
  primary checkout moved off its pinned branch" reporting rule, since
  `gh-qw` has no equivalent metadata or pin to inspect or report on. The
  skills continue to accept an ordinary clone, a `gh-qw` main worktree, or a
  linked worktree, now without inspecting any tool-specific state at all.
- Replace `docs/reference/gh-qwt.md` with `docs/reference/gh-qw.md`,
  documenting the new command surface, the `<host>/<owner>/<repo>` /
  `@<branch>` identity format, the default roots, and the two-step
  path-resolution workaround.
- This is a tool swap, not a data migration. Existing `~/ghq` clones are left
  in place; this change neither runs nor documents `gh qw migrate` against
  them.

## Alternatives Considered

### Keep gh-qwt

Works today, and changes nothing. Not adopted because `gh-qwt`'s own author
has moved development to `gh-qw`; staying on `gh-qwt` means depending on a
tool that will not receive further releases as its replacement matures,
independent of any technical difference between the two.

### Configure gh-qw to reuse the existing `~/ghq` root

Setting `GHQW_ROOT=~/ghq` or `root = "~/ghq"` in `config.toml` would let
`gh-qw` discover repositories already cloned under the old ghq-shaped root
without moving anything. Not adopted: it keeps a legacy root alive
indefinitely, leaves `gh-qw`'s own default root (`~/ghqw`) unused, and
substitutes an implicit root override for the explicit tool swap the user
asked for. New clones use the default root; migrating old ones is left to an
explicit, separate `gh qw migrate` decision if it is ever needed.

### Wait for an upstream Copilot skill or a `path`-equivalent command

`gh-qw` ships no Copilot CLI skill and no `path` command as of v0.1.0.
Waiting for either would preserve `gh-qwt`'s single-call path resolution a
little longer. Not adopted: the user-facing workflows (`ggr`, `egr`, direct
`gh qw` usage) do not depend on a skill, and the two-step
`list` / `list --exact --full-path` lookup fully replaces `path` for this
repository's needs.

### Run `gh qw migrate` against existing `~/ghq` clones as part of this change

Would consolidate every existing clone under `gh-qw`'s own root immediately.
Not adopted per explicit direction for this change: it is a tool swap only,
and any data migration is deferred to a future, separate decision.

## Consequences

- `gh-qwt`'s repository-local `qwt.managed`, `qwt.identity`,
  `qwt.defaultbranch`, and `qwt.worktreeroot` metadata no longer exists for
  any repository managed going forward; nothing reads or writes it.
- A `gh-qw` main worktree is never required to stay on a particular branch,
  so the PR skills' former "restore the pinned branch" report is gone along
  with the condition that produced it.
- Path resolution costs one extra `gh qw list` call per selection (list
  identities, then resolve the chosen one) instead of `gh-qwt`'s single
  `gh qwt path` call. The `--worktree` / no-`--worktree` branch in
  `repository-select-path` must stay in sync with `gh-qw`'s exact-match
  semantics if a future release changes them.
- `ghq` is no longer installed by this repository's `Brewfile`. Any other
  local use of the standalone `ghq` binary is now the user's own
  responsibility.
- Existing `~/ghq` clones are untouched by this change; they remain reachable
  only through plain `git`/`ghq` until someone runs `gh qw migrate`
  explicitly.
- [ADR 0008](./0008-gh-qwt.md), [ADR 0019](./0019-gh-qwt-ghq-layout.md), and
  [ADR 0023](./0023-pr-skills-gh-qwt-checkouts.md) are marked Superseded by
  this ADR.
